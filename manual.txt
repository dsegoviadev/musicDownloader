# Manual técnico de estudio — Music Downloader

## 1. Objetivo de este manual

Este documento explica el funcionamiento interno de la aplicación `musicDownloader` que estamos construyendo.

La finalidad no es solamente saber "qué hace cada archivo", sino entender **por qué está hecho así**, cómo se comunican las partes y qué conceptos de Python intervienen.

Al terminar deberías poder:

* Leer la estructura completa del proyecto.
* Entender el flujo de una búsqueda.
* Entender cómo se comunican la interfaz y los servicios.
* Trabajar con APIs HTTP.
* Trabajar con respuestas JSON.
* Entender clases y objetos.
* Entender señales de PySide6.
* Trabajar con `QTreeWidget`.
* Manipular archivos y directorios con `pathlib`.
* Utilizar `yt-dlp`.
* Manipular metadata con Mutagen.
* Entender excepciones y reintentos.
* Modificar funcionalidades existentes sin depender de ChatGPT.

# 2. Arquitectura general

La aplicación está dividida principalmente en tres capas:

```text
                    ┌─────────────────────┐
                    │   main_window.py    │
                    │       UI / Qt       │
                    └──────────┬──────────┘
                               │
             ┌─────────────────┼─────────────────┐
             │                 │                 │
             ▼                 ▼                 ▼
   ┌─────────────────┐ ┌───────────────┐ ┌────────────────┐
   │ musicbrainz.py  │ │   ytmusic.py  │ │ downloader.py  │
   │  Metadata / DB  │ │    Search     │ │    Download    │
   └─────────────────┘ └───────────────┘ └────────────────┘
             │                 │                 │
```

La idea importante es:

> `main_window.py` coordina. Los servicios hacen el trabajo especializado.

La interfaz no debería saber cómo hacer una petición HTTP a MusicBrainz ni cómo incrustar una portada en un MP3.

# 5. ¿Por qué usamos MusicBrainz?

Una de las decisiones más importantes del proyecto fue separar:

```text
METADATA
```

de:

```text
FUENTE DE AUDIO
```

MusicBrainz nos sirve principalmente para saber:

* qué artista es;
* qué álbumes tiene;
* qué tipo de release es;
* qué canciones pertenecen a un release;
* identificadores MBID.

YouTube Music se utiliza para encontrar el audio.

Por lo tanto:

```text
MusicBrainz
     =
"¿Qué canción debería buscar?"

YouTube Music
     =
"¿Dónde encuentro el audio?"

yt-dlp
     =
"Descarga el audio."

Mutagen
     =
"Escribe la información dentro del archivo."
```

Esta separación es fundamental.

Este módulo se encarga de comunicarse con MusicBrainz.

## 6.1 `_request()`

La función:

```python
def _request(url, params):
```

centraliza las peticiones HTTP.

Esto evita repetir constantemente:

```python
requests.get(...)
```

en todas las funciones.

La función recibe:

```text
url
params
```

y devuelve:

```python
response.json()
```

si todo sale correctamente.

---

# 7. Reintentos

Una parte importante es:

```python
for intento in range(3):
```

Esto significa que intentamos la petición hasta tres veces.

Después tenemos:

```python
if response.status_code in (
    429,
    502,
    503,
    504,
):
```

Estos códigos representan situaciones donde tiene sentido intentar nuevamente.

El tiempo de espera utiliza:

```python
espera = 2 ** intento
```

Por lo tanto:

```text
intento 0 → 1 segundo
intento 1 → 2 segundos
intento 2 → 4 segundos
```

Esto se conoce como **exponential backoff**.

# 10. Release Groups

MusicBrainz utiliza el concepto:

```text
release-group
```

Un release group representa conceptualmente una obra publicada.

Por ejemplo:

```text
De Mysteriis Dom Sathanas
```

puede tener distintas ediciones/releases.

La aplicación primero busca los release groups.

No pide inmediatamente todas las canciones.

Esto fue una decisión importante para evitar hacer demasiados requests.

# 11. Carga diferida de canciones

La interfaz muestra:

```text
▸ De Mysteriis Dom Sathanas
▸ Deathcrush
▸ Live...
```

pero las canciones todavía no han sido solicitadas.

Cuando el usuario abre:

```text
▾ De Mysteriis Dom Sathanas
```

se hace el request.

Esto se llama:

> Lazy loading / carga diferida.

La idea es:

```text
Buscar artista
      ↓
solo álbumes

Expandir álbum
      ↓
canciones de ese álbum
```

En lugar de:

```text
Buscar artista
      ↓
TODOS los álbumes
      ↓
TODAS las canciones
      ↓
muchísimos requests
```

# 13. Diferencia entre primary-type y secondary-types

# 25. Sanitización

Los nombres de archivos pueden contener caracteres problemáticos:

```text

\
:
*
?
"
<
>
|
```

Por eso existe:

```python

```



# 34. `Qt.UserRole`

Usamos:

```python
item.setData(
    0,
    Qt.UserRole,
    "album",
)
```

Esto permite guardar información invisible para el usuario.

Por ejemplo:

```text

    ↓

```

y:

```text

    ↓

```

y:

```text

    ↓

```

Esto es muy importante en interfaces gráficas:

> El texto visible no tiene que contener toda la información necesaria para trabajar con el objeto.

# 35. Estado de carga

Cada álbum guarda:

```python

```

como:

```text
False
```

cuando todavía no tiene canciones.

Después del request:

```text
True
```

Esto evita volver a hacer la petición si el usuario:

```text

cierra

cierra
```

# 36. Placeholder

Cuando creamos un álbum todavía no tiene canciones.

Pero queremos que Qt muestre la flecha.

Por eso agregamos:

```text
Cargando canciones...
```

como hijo temporal.

Cuando el álbum se expande:

```python
while album.childCount() > 0:
```

el placeholder se elimina.

Después aparecen las canciones reales.
